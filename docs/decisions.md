# 关键技术决策记录

记录**为什么**这样选。每条包含：背景 → 决策 → 取舍原因 → 代价。

---

## D-001：Tauri 2 而非 Electron

**背景**：需要桌面应用，要求 macOS + Windows 优先、安装包体积小、能安全访问本地文件系统。

**决策**：Tauri 2 + React 19 + Rust 后端。

**原因**：

1. Electron 每个应用带一份 Chromium（~150MB）；Tauri 用系统 WebView，安装包 ~10MB。
2. 文件系统、密钥、网络请求放在 Rust 侧，形成明确的**权限边界**——这是安全设计的基础，不只是性能优化。
3. 前端仍然写标准 React + TS，学习成本可控。

**代价**：Windows 上依赖 WebView2（Win11 自带，Win10 需安装分发器）；Rust 编译较慢；调试需要跨语言。

## D-002：pnpm monorepo，四个业务包 + 一个应用

**背景**：规格书要求 AI 服务、文件操作、UI 三者解耦，且核心逻辑要能独立测试。

**决策**：

```
apps/desktop → packages/agent → packages/storage → packages/core
```

- `core`：零依赖的纯类型与纯函数（Schema、Markdown、路径安全、文本计数）。
- `storage`：文件读写、项目模型、检索索引、提案与快照。
- `agent`：模型适配、工具定义、上下文组装、会话循环。
- `validation`：连续性 / 时间线 / 引用检查（Phase 8 填充）。

**原因**：包边界就是架构约束。`core` 不依赖 Node 内置模块，因此可以安全地打进 webview；`storage` 依赖 `FsAdapter` 抽象，同一个 `ProjectStore` 在浏览器、Node、Tauri 三种环境下都能跑，测试用 `MemoryFsAdapter` 就完全不需要真实磁盘。

**代价**：project references 配置繁琐，`pnpm` 的 workspace 符号链接在部分场景需要手动修正。

## D-003：Markdown 是唯一权威来源，索引可丢弃

**决策**：所有正文与设定都是 Markdown 文件；SQLite / 检索索引都是**可重建的缓存**。

**原因**：用户的创作不能被私有格式锁死。用 VS Code 能打开、用 Git 能管理，是这个产品的底线承诺。当索引损坏、数据库版本不兼容时，从 Markdown 重建即可，永远不会丢内容。

**连带决策**：`ProjectStore.open()` 在 `project.json` 损坏时会**重建**元数据而不是抛错拒绝打开（`.storycode/manifest.corrupt.json` 保留原文件）。曾有一个测试暴露了这个问题：损坏的 manifest 会让用户直接打不开小说——这在真实场景里是不可接受的。

## D-004：AI 只能提交 Proposal，不能写文件

**背景**：AI 改稿最大的风险是覆盖作者正在写的内容。

**决策**：工具层只暴露 `propose_create_file` / `propose_edit_file` / `propose_delete_file`。它们只往 `pending[]` 数组里追加变更，不触碰磁盘。`ProposalService.create()` 生成一个绑定 `baseContentHash` 的提案，作者在 UI 里逐项确认后才 `commit()`。

**原因**：

1. 把"AI 建议"和"实际写入"在**数据结构层面**隔开，比靠代码审查约束可靠得多。
2. `baseContentHash` 让并发冲突变成可检测的显式错误（`VersionConflictError`），而不是静默覆盖。
3. 提案本身可持久化，AI 中断后仍可恢复待审内容。

**代价**：多一次序列化与 UI 往返；同一文件在一份提案里只能出现一次（有意为之，避免自相矛盾的变更）。

## D-005：提交前自动快照 + 顺序写入 + 失败回滚

**决策**：`ProposalService.commit()` 在写任何文件前调用 `SnapshotStore.capture()`，中途任何失败都回滚已写入的文件。

**原因**：跨文件改稿（例如同时更新角色卡与三章正文）如果只成功一半，项目会进入不一致状态，这是最难排查的故障。快照 + 回滚把"部分成功"变成"要么全成要么全退"。

**代价**：快照复制文件内容，大项目下有 IO 开销；当前是顺序写入而非真正的原子事务，进程崩溃时仍依赖快照恢复（不依赖文件系统事务）。

---

## D-006：模型适配层用 `AsyncIterable<ModelEvent>`

**决策**：`ModelClient.chat()` 返回 `AsyncIterable<ModelEvent>`，事件类型为 `text-delta` / `tool-call` / `usage` / `done` / `error`。

**原因**：

1. 流式、非流式、工具调用三种行为统一成一种消费方式，Agent 循环只写一遍。
2. 取消通过 `AbortSignal` 传递，不需要在每个 provider 里重复实现。
3. 测试用 `MockProvider` 注入脚本化响应，**完全不依赖付费 API**，测试可离线、可重复。

**代价**：`AsyncGenerator` 的返回值（`AgentRunResult`）必须通过 `generator.next()` 的 `done` 分支取，调用方要小心处理。

---

## D-007：SSE 解析逻辑抽成共享解码器

**背景**：同一个模型调用有两条链路——浏览器 `fetch` 直连，以及 Tauri 里由 Rust 发起请求、把原始 SSE 文本通过事件传回前端。

**决策**：`packages/agent/src/providers/sse-decoder.ts` 提供 `ChatCompletionStreamDecoder`，两条链路都走它。

**原因**：如果各写一份，工具调用增量拼接（`tool_calls` 按 index 累积）、`usage` 捕获、CRLF 容错这些细节迟早会不一致，导致"浏览器里能用、桌面里不能用"这类最难查的 bug。

**代价**：Rust 侧要做请求与事件转发，比直接 `fetch` 多一层。

---

## D-008：API Key 只存在于系统钥匙串，webview 永远拿不到明文

**决策**：`set_api_key` / `delete_api_key` / `get_key_status` 是前端可调用的命令；`load_api_key()` 是 Rust 内部函数，**不是**命令。发起模型请求时由 Rust 读取密钥并附加 `Authorization` 头。

**原因**：只要密钥进入过一次 JS 上下文，它就可能出现在 React DevTools、内存快照、崩溃日志或前端状态持久化里。把读取权限留在 Rust 侧，前端最多知道"配没配、尾号是 1234"。

**代价**：所有模型请求必须经过 Rust 代理，无法用浏览器直连做纯前端调试（浏览器模式下明确提示不可用）。

---

## D-009：中文检索用 bigram 为主、unigram 为补充

**背景**：规格书明确要求"不能假设英文单词切分方案直接适用"。中文没有空格分隔。

**决策**：`tokenizeForSearch` 同时产生 CJK bigram（`林岚`）与 unigram（`爱`），英文按词切分。**打分时 bigram 权重高于 unigram；如果一次查询只命中了 unigram、没有任何 bigram 命中，则该文档被丢弃。**

**原因**：只切 unigram 会把「的」「在」这类高频字变成噪声。这条规则是被测试逼出来的——查询「不存在的词」曾经匹配到所有含「的」的文件，等于在**编造**检索结果。修复后该查询返回空集，符合"没有结果就说不知道"的要求。

**代价**：单字查询（如查「灯」）需要特殊处理，目前退化为 unigram 匹配，精度有限。

## D-010：上下文按层级组装并显式记录丢弃

**决策**：`assembleContext()` 按 L0（项目规则）→ L1（当前文件/选区）→ L2（邻近章节与检索结果）→ L3（角色与世界观）组装，超出 `maxTokens` 预算的内容被丢弃并记录原因。

**原因**：规格书要求"不能把整本小说复制到每次请求里"，也要求用户能看见 Agent 为什么引用某个设定。把 `included` / `dropped` 都暴露到 UI，比隐藏截断行为诚实。

**估算方式**：CJK 字符按 ≈1 token/字符，拉丁文本按 ×0.25 估算——保守但够用，不引入 tokenizer 依赖。

**已知缺陷（第一轮遗留）**：检索命中曾经只被记进 `included` 却没把正文放进 prompt，导致模型看不到证据。已修复：`PromptContext.retrieved` 会渲染成「## 检索到的相关片段」段落。

---

## D-011：Tiptap + Markdown 往返必须被测试

**背景**：规格书明确指出"不直接假定所有扩展天然支持无损转换"。

**决策**：`markdownToDoc` / `docToMarkdown` 用共享的 `MarkdownManager`，并写往返测试断言**字节级稳定**与幂等。

**原因**：序列化不稳定会导致"打开再保存，格式就变了"——对写作工具是致命的。测试还真的抓到过一次 bug：解析后的 body 多了一个前导换行，导致 `parse(serialize(x)) !== x`。

**代价**：只需要标题、段落、强调等基础语法，复杂 Markdown（表格、脚注）暂不支持往返。

---

## D-012：编辑器自动保存用 900ms 防抖 + 哈希版本校验

**决策**：输入停止 900ms 后保存；保存前重新读取文件哈希，与编辑器基线比对，不一致就弹出冲突提示（覆盖 / 重新载入），绝不静默写入。

**原因**：用户可能在 VS Code 里同时编辑同一个文件，也可能是 Agent 刚提交了提案改变了文件。静默覆盖会直接毁掉内容。

---

## D-013：Agent 会话不进 Zustand

**决策**：`AgentSession` 实例保存在模块级变量 `activeSession` 里，Zustand 只存可序列化的 UI 状态。

**原因**：`AgentSession` 持有 `AbortController`、`AsyncGenerator` 与运行时引用，不可序列化。放进 store 会破坏 devtools 快照与状态比较，也会让"重放事件流"变得不可能。

**代价**：模块级单例意味着同一时间只能跑一个任务——这恰好是产品想要的（单主 Agent），但未来若要并行任务需要改成任务注册表。

---

## D-014：exFAT 工作区导致的两个环境适配

**背景**：本仓库位于 exFAT 卷（`/Volumes/Lexar`）。

**问题与解决**：

1. **写入工具原子替换失败**：exFAT 不支持硬链接，`ENOTSUP`。改用直接写入。
2. **Tauri build script 崩溃**：macOS 会在 exFAT 上生成 AppleDouble `._*` 文件，Tauri 的权限生成器读到 `._default.toml` 时因非 UTF-8 而 panic。解决：`CARGO_TARGET_DIR=/tmp/sc-target`（APFS 路径）。
3. **Vitest 把 `._*` 当测试文件**：`test.exclude` 加 `'**/._*'`。

**教训**：这类问题与业务无关，但会让"构建失败"看起来像代码错误。把适配方式记录在此，避免下一个人重复排查。

## D-015：ESLint 的两处刻意豁免

**决策**：

1. `apps/desktop/src/**` 关闭 `@typescript-eslint/unbound-method`。Zustand 的选择器 `useStore((s) => s.save)` 返回的是普通闭包，不是类方法，该规则在此误报。
2. `packages/storage/src/memory-fs.ts` 关闭 `@typescript-eslint/require-await`。它实现的是异步接口，但内存操作本身是同步的。

**原则**：豁免必须**带注释说明原因**并限定到最小文件范围，不能全局关闭。

## D-016：不引入 UI 组件库，手写基础组件

**决策**：只用 Tailwind + 自写的 `Button` / `Dialog` / `Banner` / `Input` 等原语，不引入 shadcn/ui、Radix 等组件库。

**原因**：第一轮需要的组件不到十个；引入组件库会带来主题定制冲突、包体积和额外的依赖风险。手写能精确控制 Linear × Apple Pro 的视觉调性（尤其是深色主题的边框与层次）。

**代价**：无障碍属性、焦点管理需要自己写（`Dialog` 已实现 Escape 关闭与初始焦点）；未来组件变多时可能需要重新评估。

---

## D-017：显式 JSON 工具兼容模式

**决策**：为只返回工具文本、未产生原生 `tool_calls` 的模型提供可选的 JSON 工具协议，默认仍使用原生协议。兼容适配器把当前模式的工具 Schema 放入提示词，将工具结果转换为普通消息，并只将完整的 `{tool, arguments}` 响应解析为工具调用。最终回答支持 `{answer}` 或普通文字，普通文字不会被扫描或执行。

**安全边界**：Zod 校验完整响应与参数，限制当前模式工具白名单，复用原有 Dispatcher、路径校验和 ProposalService。混合说明文本、截断响应、非法参数不得触发工具。兼容模式等待完整响应才展示最终回答，不声称支持原生 Tool Calling。

**原因**：OpenAI 兼容的文本接口不等于支持原生函数调用；不能把普通聊天中的 JSON 示例自动当作指令执行。作者必须在模型设置中明确选择兼容模式。

## D-018：角色设定与来源一同作为 Markdown 提案审核

**决策**：角色创建与局部更新使用专用结构化工具，在产生 PendingFileChange 前完成 Zod、来源原话与引用校验。来源事实嵌入同一 Markdown 的 facts Frontmatter，并在正文管理区展示来源表；只将作者有逐字证据的字段标为 user_confirmed，其余一律保留 ai_proposed。接受文件不自动提升 AI 建议的状态。原话匹配不能替代语义与人物归属审核，歧义流程另行实现。

**更新安全**：叶字段白名单不含 id/status；已确认或已否决字段的变更必须有本轮原话，旧 fact 标为 superseded 并保留链。管理区外备注保持原文；管理区已经手改时拒绝自动再生。更新基线哈希从工作流读取时带入 ProposalService，避免模型后续轮次期间的外部修改被当作新基线。

**引用安全**：关系存储于 plot/relationships/，保留不对称视角，状态始终为 draft。依赖角色路径写入提案，关系单独接受而角色未创建时拒绝提交。暂不为每位人物反写关系 ID，读取统一通过 get_relationships，避免环形依赖与部分接受问题。

**检索**：已生成卡片只将权威 facts 放入人物检索文本；草稿细节仍可用 get_character 核对。未分级的旧卡不自动认定为权威，旧卡迁移与字段确认操作仍明确未实现。

## D-019：模型工具描述使用输入 Schema，兼容格式错误有限修复

真实模型测试发现 `z.toJSONSchema` 默认输出模式会把带默认值的可选字段列为 required，诱导模型补造年龄或用 null/0 占位。工具参数改为 `io: 'input'`；默认值由运行时校验补充，模型只需提交必要字段。另将字符 ID、空 card.relationships 等业务约束放进公开 Schema，避免接口描述与执行规则不一致。

JSON 兼容响应仅在格式/参数错误时最多修复两次，并回传具体 Schema 诊断；未知/越权工具不执行，截断不执行。普通文字只显示，不扫描嵌入 JSON。章节加载与 setEditable 的更新事件必须与真实编辑区分，以免加载产生伪保存。

---

## D-020：世界观方向由应用保存、由作者选择

候选通过工具的独立 typed outcome 进入 UI，选择作为经 Schema 校验的 AgentRunRequest 上下文传递，不能由模型在工具参数中自行伪造。候选绑定项目 ID、根目录及来源人物文件哈希。方向阶段不产生正式文件；只有作者点击选择后才允许产生 world/overview.md 的待审提案。

提案只包含选中方向；标题、时代、题材保持一致，细节保持 draft / ai_proposed。来源哈希延续到 ProposalService 创建与提交门禁，防止等待审核期间人物变化。当前拒绝覆盖已有世界观：依赖分析和持续更新尚未实现时，不以通用文件工具绕过选择/保护。

候选暂存当前聊天状态，没有伪称具备重启恢复能力；正式文件提案照常持久化。真实测试的 themes 为空，主题完整性仍需后续验收。


## D021：世界观草稿的保守局部更新

新世界观的 themes 必须显式非空，避免模型省略后默认成空数组。既有文件继续兼容原 Schema。

已有世界观先开放 themes、tone、unresolvedQuestions 三个列表字段的未确认草稿更新。工作流按对应 Markdown 标题定位区块，仅在区块与当前元数据的生成格式一致时替换，其他内容原样保留；缺失但原值为空的区块可以追加。无法证明对应关系或存在已确认来源时拒绝，避免重建整篇正文覆盖作者修改。变更附带旧值历史和原文件版本，通过 ProposalService 审核提交。完整事实冲突审核、组织规则修改与关联影响分析仍待后续实现。


## D022：世界观影响报告由存储层生成并在提交前复核

模型只能提出更新，不能自行声明“没有影响”。ProposalService 扫描真实 Markdown，为已有 world/ 文件更新 / 删除生成路径、世界观 ID、被修改旧值的匹配证据，随提案保存。命中仅代表可能有关，不代表逻辑矛盾；每文件最多展示五条证据，但保留整文件 hash。审核 UI 要求作者单独确认，后端同样检查，acceptAll 不能绕过。提交前重新扫描比对，新关联或证据文件变化需要重新生成提案。旧提案缺少报告也要求重新生成。

这是一套确定性的引用与文字影响提示，不引入付费模型或冒充完整语义分析。草稿更新已扩展到组织、阵营、规则、历史与社会冲突；更新前继续保守核对正文区块、事实来源、实体 ID 和历史引用。已确认设定冲突仍拒绝自动处理。


## D023：Markdown 阅读独立于写入，作者选择成为结构化事件

非章节 Markdown 采用 React Markdown + remark-gfm，只渲染正文，元数据默认折叠。章节提供独立阅读预览。渲染不序列化原文，不执行 HTML，不自动加载图片，避免预览引入写回或外部请求。

通用选择采用 ask_user 工具、Zod 验证和 author-question 事件，禁止从散文中猜测选项。工具成功后终止本轮后续调用，按钮点击作为明确用户输入启动下一轮。待审核提案优先，通用选项不能代替接受变更，也不能冒充世界观方向的可信选择。示例与默认文案保持中性，不注入作者其他项目的具体内容。


## D024：钥匙串等待不得阻塞桌面主线程

桌面重启采样确认同步 get_key_status 阻塞在系统凭据读取，连 AX 界面读取都超时。将设置、删除、状态查询及可用性检查的 UI 命令改为 async + spawn_blocking；OS 授权等待在后台发生，密钥不进入 webview。本地项目阅读不依赖凭据请求结束，不绕过系统钥匙串授权。


## D025：联网是显式开启的只读研究工具
